Stack Smashing Visualizer

Stack buffer overflow attacks are one of the oldest and most dangerous vulnerabilities in software. This guide explains how they work, why they're devastating, and what defenses protect against them.

Memory exploitation Control flow hijacking Critical Vulnerability

What is Stack Smashing?

Stack smashing is a technique where an attacker exploits a buffer overflow vulnerability to corrupt the stack memory, overwrite the function's return address, and redirect execution to attacker-controlled code. The attacker "smashes" through the buffer and corrupts critical control flow data.

Impact: An attacker gains arbitrary code execution with the privileges of the vulnerable program. This can lead to data theft, system compromise, malware installation, or complete takeover.

The Stack Memory Layout

Understanding the stack is critical to understanding stack smashing:

Higher Address
     +------------------+
     | Caller's Stack   |
     +------------------+
     | ... (other data) |
     +------------------+
     | Local Variables  | ← Buffer here (fixed size)
     +------------------+
     | Saved EBP        | ← Frame pointer (4 bytes)
     +------------------+
     | Return Address   | ← Where CPU jumps when function returns
     +------------------+
     | Caller's Args    |
     +------------------+
Lower Address

Key locations:

  • Buffer: Local array where input is stored (e.g., char buf[8];)
  • Saved EBP: The frame pointer, lets the function return cleanly
  • Return Address: Where execution jumps after the function returns

How the Attack Works

Step 1: Vulnerable Code

A vulnerable function lacks bounds checking:

void vulnerable(char *input) { char buf[8]; strcpy(buf, input); // ❌ No bounds check! // buf can only hold 8 bytes, but strcpy copies // as much as input provides }

Step 2: The Attacker Crafts Input

The attacker provides input longer than 8 bytes, carefully designed to:

  1. Fill the buffer (8 bytes)
  2. Overwrite saved EBP (4 bytes)
  3. Overwrite the return address (4 bytes)

Step 3: Return Address Corruption

By writing specific values to the return address, the attacker can make the CPU jump to:

  • Shellcode: Malicious code injected in the buffer itself
  • ROP gadgets: Existing code sequences chained together
  • System functions: Pre-existing library functions like system() or exec()

Step 4: Code Execution

When the function returns, the CPU reads the corrupted return address from the stack and jumps to it. The attacker's code now executes with the program's privileges.

Real-World Impact

Stack smashing has been used in:

  • Internet Worm Attacks: Morris Worm (1988) used stack smashing to propagate
  • Security Breaches: Countless server compromises exploiting unpatched buffer overflows
  • Privilege Escalation: Local users running vulnerable setuid binaries to gain root access
  • Malware Delivery: Injecting shellcode to download and execute malware

Why It's So Dangerous

  • Universal: Affects all languages that manage memory manually (C, C++, Assembly)
  • Silent: Many programs don't detect that they've been exploited
  • Powerful: Gives attacker same privileges as the program
  • Reliable: In controlled environments, can be 100% reproducible
  • Low effort: Tools like ROP compilers automate exploitation

Defense Mechanisms

1. Stack Canaries

Place a "canary" value between the buffer and return address. If overflow occurs, the canary is corrupted. Before returning, check the canary. If it's been modified, abort the program.

Defense against: Simple overflows that corrupt the return address

2. Address Space Layout Randomization (ASLR)

Randomize where memory regions load. The attacker doesn't know where shellcode or library functions are located, making it harder to craft a reliable return address.

Defense against: Attacks that target fixed addresses

3. Data Execution Prevention (DEP) / No-Execute (NX)

Mark memory pages as "data" (no execute) or "code" (execute). Stack and heap are marked non-executable, so even if shellcode is injected, it won't run.

Defense against: Direct shellcode injection

4. Bounds Checking

Use safe string functions that respect buffer sizes:

// Unsafe strcpy(buf, input); // ❌ No bounds // Safe strncpy(buf, input, 8); // ✅ Limits to 8 bytes snprintf(buf, 8, "%s", input); // ✅ Bounds checked

5. Control Flow Integrity (CFI)

Enforce that control flow only jumps to legitimate locations (function entries, exception handlers). Any other jump is invalid and the program aborts.

6. Languages and Runtime Protection

Languages like Python, Java, and Go use managed memory, eliminating buffer overflows entirely. Even in C/C++, runtime libraries can detect and prevent overflows.

Learning Objectives

After working with the Stack Smashing Visualizer, students should be able to:

  • Explain the stack memory layout and the role of each section
  • Describe how a buffer overflow leads to return address corruption
  • Understand why the return address is a critical control flow target
  • Recognize vulnerable code patterns (unbounded strcpy, sprintf, gets)
  • Explain how stack canaries, ASLR, DEP, and CFI provide defense
  • Identify when input validation and bounds checking are necessary

Sample Attacks

  • Small Overflow: Overwrite only part of the buffer
  • Medium Overflow: Overwrite buffer and start corrupting saved EBP
  • Large Overflow: Overwrite everything including return address
  • NOP Sled: Use NOP (0x90) instructions followed by shellcode

Discussion Questions

  • Why is strcpy considered dangerous in modern code?
  • How would a stack canary detect this overflow?
  • If ASLR is enabled, how does it make this attack harder?
  • Why is NX/DEP alone not sufficient to prevent all stack smashing attacks?
  • What's the relationship between this vulnerability and privilege escalation?
  • Why can't you just "check if the input is too long" after calling strcpy?
