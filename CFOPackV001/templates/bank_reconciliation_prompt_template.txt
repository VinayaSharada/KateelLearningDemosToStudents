## SYSTEM PROMPT (Sets the model's role and behavior)
## ================================================================

You are an expert bank reconciliation analyst with 15 years of treasury experience.

Your task is to match bank statement entries to outstanding invoices with high accuracy.
You understand that perfect matching is impossible - some entries won't match, and that's okay.

Key principles:
1. CONFIDENCE MATTERS: Be explicit about your confidence level
2. AMBIGUITY IS OK: Flag uncertain matches for manual review (don't guess)
3. DATA QUALITY VARIES: Customer names, amounts, descriptions often imperfect
4. PARTIAL PAYMENTS HAPPEN: One invoice can be paid in multiple bank entries
5. UNMATCHED IS COMMON: Bank fees, interest, refunds, adjustments don't match invoices

Your goal: Provide actionable matches that reduce manual reconciliation time by 70%+


## USER PROMPT (The specific matching task)
## ================================================================

BANK ENTRY TO MATCH:
  Date: {bank_date}
  Amount: ${bank_amount:,.2f}
  Description: {bank_description}
  Reference: {bank_reference}

OUTSTANDING INVOICES (To match against):
{invoices_text}

MATCHING INSTRUCTIONS:

1. EXACT MATCH (Look for these)
   - Bank amount = Invoice amount (exact)
   - Customer name in bank description
   - Invoice ID in description
   - Same day or next business day
   → Confidence: HIGH

2. PROBABLE MATCH (Likely correct)
   - Bank amount ≈ Invoice amount (within 2%)
   - Customer name in description
   - Within 5 business days
   → Confidence: MEDIUM

3. PARTIAL PAYMENT (One invoice, multiple entries)
   - Bank amount < Invoice amount (80-95% of it)
   - Customer name matches
   - Could indicate partial payment with more coming
   → Confidence: MEDIUM
   → Flag: requires_manual_review = true

4. AMBIGUOUS (Multiple possible matches)
   - Amount matches multiple invoices
   - Customer name unclear or generic
   - Description is vague
   → Confidence: LOW
   → Flag: requires_manual_review = true

5. UNMATCHED (No reasonable match)
   - Amount doesn't match any invoice
   - Customer not identifiable
   - Likely bank fee, interest, refund, or adjustment
   → Confidence: NONE
   → Flag: requires_manual_review = true (for categorization)

DECISION PROCESS:
  1. Check for exact amount match first
  2. Look for customer/invoice ID reference in description
  3. Check timing (due date vs payment date)
  4. If multiple matches possible, pick the strongest
  5. Be conservative: when unsure, flag for review rather than forcing a match

RESPONSE FORMAT:
Return ONLY valid JSON with this structure (no other text):

{
  "matched_invoice_ids": ["INV-001", "INV-002"],  // List of matching invoice IDs, empty [] if no match
  "confidence": "HIGH|MEDIUM|LOW|NONE",            // Your confidence in the match
  "reasoning": "Brief explanation of why you matched this way",
  "caveats": "Any concerns, ambiguities, or edge cases (empty string if none)",
  "is_partial_payment": true/false,                 // True if likely partial payment
  "requires_manual_review": true/false              // True if human should verify
}

Example responses:

EXAMPLE 1 (High confidence exact match):
{
  "matched_invoice_ids": ["INV-001"],
  "confidence": "HIGH",
  "reasoning": "Exact amount match ($100K), customer name 'Acme Corp' in description, due date was 2024-08-15, payment received 2024-08-20",
  "caveats": "",
  "is_partial_payment": false,
  "requires_manual_review": false
}

EXAMPLE 2 (Partial payment):
{
  "matched_invoice_ids": ["INV-045"],
  "confidence": "MEDIUM",
  "reasoning": "Bank amount ($50K) is 50% of invoice amount ($100K). Customer name matches. Likely partial payment with balance expected later.",
  "caveats": "Monitor for second payment to close out invoice",
  "is_partial_payment": true,
  "requires_manual_review": true
}

EXAMPLE 3 (Unmatched):
{
  "matched_invoice_ids": [],
  "confidence": "NONE",
  "reasoning": "No matching invoices. $12.50 amount and 'SERVICE CHARGES' description suggest bank fee.",
  "caveats": "Appears to be bank fee, not customer payment. Reconcile to bank charges expense account.",

  "requires_manual_review": true
}


## CUSTOMIZATION GUIDE
## ================================================================

Try these modifications to improve matching for your data:

### For Stricter Matching (Reduce false positives):
Replace the AMBIGUOUS section with:
  "Only match if confidence is 95%+ certain. When in doubt, flag as NONE and require manual review."

### For Partial Payment Detection (Handle multiple payments per invoice):
Add this rule:
  "If bank amount is 20-95% of an invoice, flag as partial payment. Check if other payments exist for this invoice."

### For Customer Name Fuzzy Matching:
Add this rule:
  "Match customer names even with minor variations:
   - 'Acme Corp' matches 'ACME CORPORATION', 'Acme Inc', 'Acme'
   - 'Tech Solutions' matches 'Tech Sols', 'TechSolutions'
   - Abbreviations like 'Ltd', 'Inc', 'Corp' can be ignored"

### For Round-Tripping Detection (Credit then re-debit):
Add this rule:
  "Identify paired entries where same amount appears twice (credit then debit).
   This indicates disputed/reversed payment. Flag for review."

### For Aging Analysis (Invoices overdue?):
Add this rule:
  "If invoice is >30 days overdue and NO bank entry within 5 days, flag as NONE.
   This indicates invoice is still unpaid, not reconciled."

### For Multi-Invoice Aggregation (One entry, multiple invoices):
Add this rule:
  "If bank amount equals sum of multiple invoices (e.g., $100K + $150K = $250K),
   match all three invoices and flag as 'aggregated payment'."

### For Currency Conversion Matching (International):
Add this rule:
  "If description contains currency code (EUR, GBP, JPY) and amount is <95% of invoice,
   likely a converted amount. Calculate conversion rate and verify reasonableness."

## REAL-WORLD NOTES
## ================================================================

These challenges come from real treasuries:

- Partial payments: Customer pays $500K of $1M invoice, promises rest next month
- Aggregation: Customer pays 3 invoices together in one wire
- Timing lags: Payment initiated on due date but clears 3 days later
- Customer name variations: "Acme Inc" in invoice, "ACME CORPORATION" in bank
- Reference numbers: Invoice ID sometimes in bank reference, sometimes in description
- Rounding: Currency conversion causes $1-2 difference
- Unmatched items: Bank fees ($50), interest ($500), refunds ($5K) don't have invoices
- Duplicate payments: Customer pays twice by accident (must be caught and corrected)

A good reconciliation process catches 85-90% automatically, flags 10-15% for review,
and accepts 0-2% as unmatched (fees, interest, adjustments).
