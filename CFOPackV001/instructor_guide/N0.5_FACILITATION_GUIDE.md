## Module Overview

This optional module teaches participants how to use Small Language Models (SLMs) locally to automate a real treasury workflow: matching bank statement entries to outstanding invoices.

**Why this matters:**
1. Real work: Treasurers do this reconciliation manually or with Excel
2. Data privacy: No external API calls (Claude, OpenAI) required
3. Cost-effective: Run reconciliation unlimited times (free after setup)
4. Practical: Shows where LLMs help AND where they struggle

**What participants learn:**
- How to run language models locally (ollama)
- Prompt engineering for structured tasks
- Understanding LLM limitations
- Data privacy vs. accuracy tradeoff

## Workshop Flow

### Segment 1: Problem Framing (5 min)

**The Real Problem:**

> "Every treasurer has done this: bank reconciliation. You have a bank statement with 500 entries. You have 300 invoices outstanding. You need to match them: which invoices have been paid, which are partial payments, which haven't been touched?
>
> Most treasuries do this in Excel. Manually. It's tedious, error-prone, and eats time that could go to analysis.
>
> The dream: Automate 80-90% of matching, flag uncertain cases for human review."

**The Constraint:**

> "But here's the problem: If you upload your bank statement and invoices to Claude API or ChatGPT, it leaves your company. Your CFO will shut it down for compliance/security reasons. You can't risk client data in the cloud.
>
> Solution: Run a small language model locally, in your notebook, on YOUR infrastructure. Data never leaves."

**The Question:**

> "Today's challenge: Can we build a local reconciliation tool that's good enough? What works? Where does it struggle? How do we prompt it to improve?"

## Challenges Demonstrated

### Challenge 1: Partial Payments

**The scenario:**
- Invoice: $100,000
- Bank entry 1: $60,000 (payment received)
- Bank entry 2: (not yet received)

**Why it's hard:**
- Simple matching looks for $100K in bank → finds nothing
- Smarter matching needs to recognize "$60K is part of $100K"
- Requires context about expected payment behavior

**Teaching point:**
> "This is why automation can't be 100%. Partial payments need human judgment: Is $60K definitely for this invoice, or could it be for something else? The model can flag it, but human says 'yes, that's it.'"

### Challenge 2: Data Quality Issues

**The scenario:**
- Invoice: "Tech Innovations Inc"
- Bank entry: "Tech Innov INC" (abbreviated, mixed case)

**Why it's hard:**
- Exact string matching fails
- Fuzzy matching helps but requires tuning
- Phi-3 can handle some variation, but not perfectly

**Teaching point:**
> "Garbage in, garbage out. If bank descriptions are inconsistent, even a perfect model struggles. The best fix: standardize data at the source (require consistent customer names)."

### Challenge 3: Unrelated Entries

**The scenario:**
- Bank statement includes fees, interest, refunds
- No matching invoices (these aren't customer payments)

**Why it's hard:**
- Model assumes everything should match something
- Actually: many entries are internal (not invoice-related)
- Need to teach model to recognize categories

**Teaching point:**
> "Real bank statements have lots of noise. A good reconciliation process first categorizes: Is this a customer payment, a fee, interest, a transfer? Only then tries to match payments to invoices."

### Challenge 4: Ambiguity

**The scenario:**
- Bank entry: $500,000 (no customer name)
- Invoices: Invoice A ($500K), Invoice B ($480K), Invoice C ($520K)

**Why it's hard:**
- Could legitimately match any of three
- Model must pick one or flag as ambiguous
- Human judgment needed: Which is most likely?

**Teaching point:**
> "When the data is ambiguous, the model is ambiguous. That's not a model failure—it's honest. A good system flags ambiguity and asks a human."

## What Works Well

✅ **Exact matches** - Bank amount = Invoice amount + customer reference  
✅ **Timing-based matching** - Invoice due date aligns with payment date (±5 days)  
✅ **Clear customer names** - "Acme Corp" in both systems  
✅ **Invoice IDs** - Invoice number explicitly in bank description  
✅ **Bulk categorization** - Identifying which entries are fees vs. payments  

---

## What Struggles

❌ **Partial payments** - One invoice, multiple payments (or vice versa)  
❌ **Name variations** - "Tech Inc" vs "Tech Innovations Inc"  
❌ **Ambiguous amounts** - Could match multiple invoices  
❌ **Foreign exchange** - Amounts differ due to conversion rates  
❌ **Round-tripping** - Payment, then credit, then re-payment  
❌ **Data quality** - Garbage descriptions make matching impossible

## Teaching Points

### Point 1: Local Models for Privacy

**Statement:**
> "Cloud models like Claude are powerful but send data externally. For financial data, this is often prohibited. Local models let you keep data on-premises while getting AI benefits."

**Trade-off:**
- Cloud (Claude): Better quality, instant, requires external service
- Local (Phi-3): Lower quality, slower, but data stays local

**Real world:**
> "Many banks and treasuries now run local language models for exactly this reason. The quality is 'good enough' (80-90%) and the privacy is guaranteed."

### Point 2: Prompt Engineering Matters

**Statement:**
> "You don't always need a better model. Sometimes you just need better instructions. Small changes to prompts can significantly improve results."

**Example:**
- "Match if reasonable" → Gets 3 ambiguous matches
- "Only match if 95%+ confident" → Gets 1 ambiguous match (safer)

**Lesson:**
> "Before you blame the model, try improving the prompt. It's free and often works."

### Point 3: Good Data is Essential

**Statement:**
> "AI can't fix bad data. If your bank statements have vague descriptions and inconsistent naming, no amount of prompting will help."

**Solution:**
- Standardize customer names across systems
- Require invoice ID in bank descriptions
- Clean data before reconciliation

**Real world:**
> "The best reconciliation systems start with clean, standardized data. Then the model has a fighting chance."

### Point 4: Automation ≠ Replacement

**Statement:**
> "This tool doesn't replace the treasurer. It augments them. It handles 80-90% of obvious cases, freeing the treasurer to focus on the tricky 10-20%."

**The spectrum:**
```
Manual 100%        → Human reviews all 500 entries (8 hours)
+This tool (80%)   → Model matches 400, human reviews 100 (2 hours)
+Clean data (95%)  → Model matches 475, human reviews 25 (30 min)
```

**Lesson:**
> "Automation is about human amplification, not replacement."

## Common Questions & Answers

**Q: Why is Phi-3 so slow compared to Claude?**

A: Phi-3 is running locally on your CPU/GPU (no cloud connection). Claude's speed is partly from massive inference infrastructure (thousands of GPUs in parallel). For privacy, the slowness is acceptable.

---

**Q: Can I use a bigger model like Llama-70B?**

A: Not practically in Colab (runs out of memory). Llama-70B is ~40GB. Colab's GPUs have 15-40GB total VRAM. Phi-3 (2.3GB) fits easily. There's a quality/size tradeoff.

---

**Q: What if ollama installation fails?**

A: The notebook falls back to heuristic matching (simple rules). It's slower learning but still shows the concepts. The real lesson is: design systems to degrade gracefully.

---

**Q: Can I use this with my real bank data?**

A: Yes. Replace the CSV files with your actual bank statement and outstanding invoices. Results will vary based on your data quality. Test with a small subset first.

---

**Q: Is this better than Excel VLOOKUP?**

A: Different tools for different jobs.

| Task | Excel VLOOKUP | This LLM Tool |
|------|---|---|
| Exact matches | Fast, simple | Overkill |
| Fuzzy matches | Difficult, error-prone | Natural |
| Partial payments | Impossible | Possible |
| Ambiguity handling | N/A | Explicit |
| Privacy | Local | Local |

Use LLM when you need to handle messy, ambiguous data.

---

**Q: Why not use Claude API instead of ollama?**

A: You could. But then your bank data and invoices go to Anthropic's servers. For sensitive data, many organizations can't do this. Local models guarantee privacy (no external calls).

---

**Q: How do I improve the matching?**

A: In order of impact:

1. **Clean the data first** (Rename customers consistently, standardize formats)
2. **Customize prompts** (Edit templates/bank_reconciliation_prompt_template.txt)
3. **Use bigger model** (Switch to Mistral-7B if resources allow)
4. **Add context** (Invoice IDs in bank descriptions, customer codes)
5. **Hybrid approach** (Use heuristics for high-confidence matches, LLM for ambiguous)

## Extension Ideas

### Extension 1: Round-Trip Detection

Enhance the prompt to detect paired credits/debits (payment, then reversal, then re-payment). Real treasuries see this with disputed invoices.

### Extension 2: Multi-Invoice Aggregation

Teach the model to recognize when one bank entry equals the sum of multiple invoices (e.g., customer pays 3 invoices together).

### Extension 3: Currency Conversion Verification

For international payments, verify that converted amounts match invoiced amounts within expected FX rates.

### Extension 4: Aging Analysis

Flag invoices that are >30 days overdue and still unmatched (indicates they're still unpaid, at risk).

### Extension 5: Supplier Reconciliation

Reverse the logic: Match bank outflows to supplier invoices (payables reconciliation instead of receivables).

## Troubleshooting

**Problem: Ollama installation fails in Colab**
- Solution: Fall back to demo mode (show pre-run results)
- Lesson: Robust design includes graceful fallbacks

**Problem: Model download is very slow**
- Solution: Pre-download to Google Drive, load from there
- Prevention: Tell participants in advance, allow background download

**Problem: Reconciliation is taking 5+ minutes**
- Solution: Run on fewer entries (first 10), extrapolate
- Prevention: Mention Phi-3 is slow, show timing expectations

**Problem: Results are mostly "NONE" (no matches)**
- Solution: Check data alignment; are invoice IDs matching?
- Prevention: Run data validation first (ensure IDs overlap)

**Problem: Participants want to customize but get errors**
- Solution: Provide error messages from notebook, walk through fix
- Prevention: Have 2-3 tested prompt variants ready to use
