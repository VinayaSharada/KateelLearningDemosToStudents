## Module Purpose

This optional module teaches participants how to **use local language models to automate bank reconciliation** - a real treasury workflow that every CFO does manually or via Excel.

**The Problem:** Bank statements have messy data, partial payments, naming variations. Matching to outstanding invoices is tedious and error-prone.

**The Solution:** Use Phi-3 (small language model) running locally to automate matching while keeping sensitive financial data on-premise (not sent to external APIs).

**The Value:** 
- 70-80% of matches automated (reduce 4-hour task to 1 hour)
- Data privacy guaranteed (no cloud API calls)
- Prompt engineering teaches broader skills
- Shows practical LLM use beyond chatbots

## What's Included

### 1. Main Notebook: `N0.5_Bank_Reconciliation_Assistant.py`

**What it does:**
- Installs/checks for ollama (local LLM server)
- Downloads Phi-3 (or Mistral-7B) model
- Loads synthetic bank statement + invoices
- Runs reconciliation matching loop
- Generates results with match confidence
- Flags ambiguous/unmatched entries for manual review

**Inputs:**
- `data/synthetic/bank_statement.csv` (25 sample entries)
- `data/synthetic/outstanding_invoices_for_reconciliation.csv` (12 invoices)

**Outputs:**
- `outputs/N0.5_reconciliation_results.csv` (full matching details)
- `outputs/N0.5_reconciliation_summary.csv` (statistics)
- `outputs/N0.5_unmatched_invoices.csv` (still-outstanding)

**Fallback Mode:**
If ollama isn't available, uses heuristic matching (rules-based). Slower but works without LLM.

### 2. Synthetic Data: `data/synthetic/bank_statement.csv`

25 bank entries demonstrating:

| Ambiguous entries | 2 | Could match multiple invoices |
| Data quality issues | 2 | Name variations, unclear descriptions |
| Unmatched items | 4 | Bank fees, interest, refunds (not invoices) |

### 3. Synthetic Data: `data/synthetic/outstanding_invoices_for_reconciliation.csv`

12 outstanding invoices from 8 customers:
- Mix of industries

## What Works Well ✓

- **Exact amount matching:** Bank entry $250K matches invoice $250K perfectly
- **Customer name matching:** "Midwest Logistics" recognized across variations
- **Invoice ID references:** Explicit ID in bank description → definitive match
- **Timing analysis:** Payment date vs. invoice due date alignment
- **Partial payment detection:** Recognizes when payment is less than invoice
- **Unmatched categorization:** Identifies fees, interest, refunds correctly

---

## What Struggles ✗

- **Name variations:** "ACME CORP" vs "Acme Inc" (model is literal, needs fuzzy matching)
- **Multiple possible matches:** Amount could match 2-3 invoices (ambiguity)
- **Data quality issues:** Vague descriptions, missing customer info
- **Partial payments:** One invoice, multiple payments (requires tracking state)
- **Refunds vs. payments:** Opposite directions, needs type awareness
- **Round-tripping:** Payment → dispute → credit → re-payment (complex logic)

**Why these limitations?** Phi-3 (3.8B) is smaller than Claude (100B+). Smaller = more literal, less able to reason about ambiguity.

## Customization Guide

Students can improve matching by editing the prompt. Examples:

### To reduce false positives (stricter):
```
"Only match if confidence is 95%+ certain. 
 Better to flag for review than to incorrectly match."
```

### To handle partial payments better:
```
"If bank amount is 20-95% of invoice and customer names match,
 flag as probable partial payment."
```

### To handle name fuzzy matching:
```
"Match customer names even with variations:
 'Acme Corp' matches 'ACME CORPORATION', 'Acme Inc', etc."
```

## Model Selection

### Phi-3 (3.8B) - Recommended
- **Size:** 2.3 GB
- **Speed:** ~5-10 sec per match
- **Quality:** Good (80-90% accuracy)
- **Pros:** Fits easily in Colab/laptop, free
- **Cons:** Slower than larger models, less accurate on ambiguous cases
- **Best for:** Privacy-critical organizations, high-volume reconciliation

### Mistral-7B (7B)
- **Size:** 4.1 GB
- **Speed:** ~15-20 sec per match
- **Quality:** Excellent (90-95% accuracy)
- **Pros:** Better quality than Phi-3
- **Cons:** Needs more resources, slower
- **Best for:** Accuracy-critical work, fewer entries

### Claude API
- **Speed:** <1 sec per match
- **Quality:** Excellent (95%+ accuracy)
- **Cost:** ~$0.001 per match ($5 for 5000 entries)
- **Privacy:** Data sent to Anthropic
- **Best for:** Non-sensitive data, small batches, when accuracy is critical

## Real-World Application

### Your Own Data

To use this with real company data:

1. **Export** your bank statement and outstanding invoices as CSV
2. **Match** the CSV columns to the synthetic data format
3. **Load** in N0.5 (just change the file paths)
4. **Run** reconciliation
5. **Review** results and iterate on prompts

### Scaling Up

If you have 500+ monthly reconciliations:

1. **Automate** HIGH confidence matches (56%) → no review
2. **Flag** MEDIUM confidence (24%) → AR manager review (10 min each)
3. **Route** unmatched (20%) → Finance for categorization
4. **Result:** 4-hour manual task → 45 minutes total

### Cost vs. Manual

```
Manual (100 entries):        2.5 hours = $150 (AP staff time)
N0.5 + Review (100 entries):  40 min = $25 (staff time only, model is free)
Savings:                      ~$125 per 100 entries
```

## Troubleshooting

**Q: Ollama won't install in Colab**

A: Use demo mode instead. Show pre-generated results. The lesson is learning the concepts, not the tools.

---

**Q: Model download is too slow**

A: Pre-download to Google Drive. Share the folder. Participants mount it instead of downloading fresh.

---

**Q: Results are mostly "no matches"**

A: Check data alignment. Are invoice IDs actually in the bank statement? If not, both files need adjustment.

---

**Q: Can I use this with real invoices and real bank data?**

A: Yes. Just replace the CSV files. Results will vary based on your data quality. Test with 20-50 entries first.

---

**Q: Is this better than Excel VLOOKUP?**

A: Different tools:
- VLOOKUP: Fast for exact matches, can't handle partial payments or ambiguity
- N0.5: Slower, but handles fuzzy matching, ambiguity, partial payments

Use N0.5 when data is messy. Use VLOOKUP when data is clean.

## Questions?

- **How does this connect to N1-N8?** N0.5 cleans data; N1-N8 analyzes clean data
- **Do I have to use Phi-3?** No, you can use Mistral-7B (bigger) or Claude API (cloud-based)

- **What if data quality is really bad?** Model will struggle. Better to fix data first, then reconcile.
- **Is this production-ready?** It's a teaching tool. The concepts are production-ready; adapt as needed for your systems.
